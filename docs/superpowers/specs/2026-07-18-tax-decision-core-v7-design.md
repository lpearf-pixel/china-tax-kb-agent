# 中国税务知识库 Agent V7.0 税务决策核心设计

## 1. 设计状态

- 状态：已批准进入正式设计
- 设计日期：2026-07-18
- 基础分支：`agent/tax-planning-workbench-v6`
- 目标分支：`agent/tax-decision-core-v7`
- 上游知识库版本：`KB-2026.07.17-V5-PILOT-XJ-HI`
- 第一阶段税种：增值税
- 第一阶段地域：全国、新疆维吾尔自治区、海南自由贸易港

## 2. 目标

将 V6 的“结构化表单 + A 级法规检索 + 固定方案模板”升级为可审计的税务决策核心，使系统能够：

1. 描述多主体、多合同、多资金流、多发票流和多货物流的真实交易；
2. 将自然语言业务拆解成明确的税务议题；
3. 通过外部化规则而不是硬编码判断政策适用性；
4. 计算不同方案的税额、现金流时间和敏感性结果；
5. 在修改金额、日期、发票需求或主体身份后，仅重算受影响节点；
6. 将每项结论追溯到事实、规则、法规条款和计算过程；
7. 在法规变更后自动识别受影响案件并标记重新评估；
8. 保持高风险事项的人工审签门禁。

V7.0 不追求一次性覆盖所有税种，也不建设完全自由的多 Agent 系统。第一阶段只建立可扩展的决策内核，并以增值税、小规模纳税人、新疆和海南场景证明架构有效。

## 3. 非目标

V7.0 不包含以下范围：

- 不自动替代注册税务师、律师或主管税务机关的最终认定；
- 不直接生成申报表并自动申报；
- 不建设完整会计总账系统；
- 不一次性实现企业所得税、个人所得税、土地增值税等全部计算器；
- 不允许 LLM 自行创造税率、优惠条件、HS 编码或享惠主体资格；
- 不允许通过虚假合同、虚开发票、隐藏收入或人为分拆等方式设计方案；
- 不将真实企业敏感资料默认上传 GitHub 或外部模型服务。

## 4. 架构选择

采用“确定性决策核心 + 受限 LLM 辅助”的架构：

```text
用户访谈、合同摘要、交易资料
        ↓
事实图谱与事实版本
        ↓
税务议题树
        ↓
法规证据检索与版本过滤
        ↓
规则引擎
        ↓
税务计算与现金流引擎
        ↓
情景生成与方案排序
        ↓
风险门禁与人工审签
        ↓
Obsidian 报告、审计轨迹和案件状态
```

确定性组件负责事实校验、规则匹配、税额计算、状态迁移和证据追踪。LLM 后续只能用于：

- 将用户自然语言映射为候选事实；
- 生成需要用户确认的问题；
- 对确定性结果进行通俗解释；
- 根据已有证据和计算结果整理报告。

LLM 输出不得直接改变正式事实、规则结果或计算值，所有修改必须经过显式确认或确定性校验。

## 5. 模块边界

### 5.1 事实图谱模块

负责描述案件中真实存在的实体和关系。

核心节点：

- `Party`：企业、自然人、个体工商户、其他组织；
- `TaxRegistration`：增值税身份、登记日期、主管机关；
- `Transaction`：交易类型、发生日期、金额、含税状态；
- `Contract`：合同主体、标的、价税条款、付款条件；
- `InvoiceFlow`：开票方、受票方、发票类型、金额和时间；
- `CashFlow`：付款方、收款方、金额、时间和用途；
- `GoodsFlow`：货物起点、终点、海关流向、用途；
- `ServiceFlow`：实际服务提供方、接受方、履约地；
- `Asset`：不动产、设备、无形资产及权属；
- `Relationship`：股权、控制、关联、代理、委托关系；
- `EvidenceDocument`：合同、发票、报关单、流水、台账。

核心关系：

```text
Party --signs--> Contract
Contract --governs--> Transaction
Transaction --has_invoice_flow--> InvoiceFlow
Transaction --has_cash_flow--> CashFlow
Transaction --has_goods_flow--> GoodsFlow
Party --controls/relates_to--> Party
Party --owns--> Asset
EvidenceDocument --supports--> Fact
```

事实必须具有：

- `fact_id`；
- 来源；
- 事实状态：`asserted / confirmed / contradicted / superseded`；
- 生效时间；
- 录入时间；
- 敏感等级；
- 确认人和确认时间。

事实图谱以本地 JSON 为运行时格式，以 Obsidian Markdown 为人工审阅和归档格式。图谱不是独立真相源，正式事实仍需回链到原始资料和用户确认记录。

### 5.2 税务议题树模块

负责把一个业务拆成可分别判断的税务问题。

每个议题包含：

- `issue_id`；
- 税种；
- 问题类型；
- 相关主体和交易；
- 必要事实；
- 缺失事实；
- 候选规则；
- 风险等级；
- 当前状态。

增值税第一阶段议题类型：

- 是否属于应税交易；
- 纳税人和纳税义务主体；
- 小规模或一般纳税人身份；
- 一般纳税人登记义务；
- 计税期间；
- 起征点适用；
- 3% 减按 1% 适用；
- 不动产和土地使用权排除；
- 发票和放弃优惠；
- 跨地区预缴；
- 海南普通交易或自贸港特殊交易；
- 海南享惠主体、HS 编码、流向和用途门禁；
- 关联分拆或缺乏合理商业目的风险。

议题树必须支持父子关系。例如“海南进口设备税务处理”下包含主体资格、商品目录、进口环节税、二线流转和后续处置等子议题。

### 5.3 规则 DSL 与规则引擎

法规适用逻辑从 Python 业务代码中移出，存放在版本化规则文件中。

第一阶段使用 YAML 规则 DSL，规则结构至少包含：

```yaml
rule_id: VAT-SMALL-THRESHOLD-QUARTER-2026
version: 1
status: effective
valid_from: 2026-01-01
valid_to: 2027-12-31
jurisdiction: CN
tax_type: 增值税
priority: 100

when:
  all:
    - fact: taxpayer.vat_status
      operator: equals
      value: 小规模纳税人
    - fact: transaction.amount_period
      operator: equals
      value: 季度
    - fact: transaction.sales_amount
      operator: less_or_equal
      value: 300000

then:
  outcome: threshold_exempt_candidate
  value: true
  confidence: deterministic

requires:
  - transaction.total_sales_same_period
  - invoice.waive_exemption

legal_basis:
  - document_id: DOC-CN-VAT-MOF-STA-2026-10
    provision_id: PROV-VAT-ANN10-THRESHOLD
```

规则引擎要求：

- 支持 `all / any / not` 条件组；
- 支持字符串、数字、日期、集合和布尔比较；
- 支持规则优先级和冲突检测；
- 支持全国规则叠加新疆或海南覆盖规则；
- 支持有效期过滤；
- 支持排除规则；
- 支持输出缺失事实；
- 支持记录命中、未命中和排除原因；
- 不允许在 YAML 中执行任意代码；
- 规则加载失败时停止正式分析，不静默降级为模型猜测。

规则结果分为：

- `applicable`；
- `not_applicable`；
- `insufficient_facts`；
- `conflict`；
- `manual_review_required`。

### 5.4 税务计算引擎

V7.0 首先实现增值税和直接相关现金流计算，不一次性覆盖全部税种。

计算输入：

- 含税或不含税金额；
- 计税期间；
- 纳税人身份；
- 税率或征收率；
- 是否适用起征点；
- 是否适用减按征收；
- 是否放弃优惠；
- 发票类型；
- 进项税额；
- 预缴税额；
- 交易和申报时间。

计算输出：

- 不含税销售额；
- 应纳增值税；
- 可抵扣进项；
- 应补或应退金额；
- 税款发生和支付时间；
- 计算公式；
- 使用的规则结果；
- 舍入方法；
- 结果状态：确定、条件确定或无法计算。

第一阶段计算场景：

1. 小规模纳税人起征点候选；
2. 小规模 3% 减按 1%；
3. 放弃免税或减税开具专用发票；
4. 一般纳税人销项减进项基础测算；
5. 超过 500 万元的身份敏感性提示；
6. 海南特殊政策资格未确认时的普通税制保守基线。

货物进口、关税、消费税和海南零关税在 V7.0 中只提供“普通税制基线 + 所需输入 + 人工复核”，不在缺少完整税则数据时输出确定税额。

所有金额计算使用 `Decimal`，禁止使用二进制浮点数。舍入规则在配置中统一定义，并在报告中展示。

### 5.5 情景与方案引擎

方案不能再是固定文案，而是由“可变决策变量 + 不可变真实事实 + 规则和计算结果”生成。

不可改变的事实示例：

- 真实交易标的；
- 实际履约主体；
- 实际货物流和资金流；
- 已发生业务日期；
- 真实关联关系。

可比较的合法决策变量示例：

- 是否放弃免税并开具专用发票；
- 报价采用含税或价税分离；
- 收款和开票节奏；
- 未来是否自愿登记一般纳税人；
- 在优惠资格确认前采用普通税制预算还是优惠情景预算；
- 合同中的政策变化和税费承担条款。

方案引擎流程：

```text
生成决策变量组合
→ 排除违法或与事实矛盾组合
→ 对每个组合运行规则引擎
→ 运行计算和现金流模型
→ 计算风险与资料完备度
→ 按用户目标排序
```

每个方案至少输出：

- 方案名称；
- 决策变量；
- 税额和现金流；
- 法规依据；
- 适用前提；
- 执行动作；
- 资料清单；
- 风险；
- 与基线差异；
- 是否需要人工审签。

排序不是单一“税最少”，而是根据用户目标生成多维评分：

- 税负；
- 现金流；
- 法规确定性；
- 资料完备度；
- 执行复杂度；
- 稽查和争议风险；
- 客户发票需求满足程度。

系统必须展示评分构成，不能只给黑箱总分。

### 5.6 案件状态机与版本管理

案件状态：

```text
draft
→ facts_pending_confirmation
→ issues_identified
→ evidence_ready
→ rules_evaluated
→ calculation_ready
→ scenarios_ready
→ human_review_pending
→ approved / rejected
→ affected_by_law_change
→ archived
```

状态迁移必须满足前置条件。例如缺少业务日期时不能进入 `evidence_ready`，存在规则冲突时不能直接进入 `approved`。

案件需要保存：

- `case_id`；
- 事实版本；
- 议题版本；
- 规则集版本；
- 知识库版本；
- 计算版本；
- 方案版本；
- 审签状态；
- 时间线事件。

修改某个事实时，系统计算影响范围并只重跑相关节点。例如修改“客户需要专票”时，不需要重新识别主体和地域，但需要重跑优惠放弃、税额和方案排序。

### 5.7 法规变更影响模块

法规更新发布后，根据 `document_id / provision_id / rule_id` 建立影响链：

```text
法规条款
→ 规则
→ 税务议题
→ 历史案件
→ 方案和审签结论
```

当规则有效期、税率、起征点或排除条件变化时：

- 标记引用该规则的案件为 `affected_by_law_change`；
- 记录旧规则和新规则；
- 生成差异摘要；
- 不自动覆盖已批准方案；
- 由用户或审签人决定是否重新计算；
- 历史业务仍使用当时有效的规则版本。

采用双时间字段：

- `valid_time`：法规和事实实际适用时间；
- `system_time`：知识库录入、修改和发布的时间。

## 6. 数据存储设计

保持 Obsidian 为人工知识事实源，同时增加本地运行数据目录：

```text
rules/
  vat/
    national/
    xinjiang/
    hainan/

cases/
  <case_id>/
    case.json
    facts-v001.json
    issues-v001.json
    decisions-v001.json
    calculations-v001.json
    scenarios-v001.json
    timeline.jsonl

16-交互工作台/会话记录/
  <case_id>.md
```

约束：

- `rules/` 进入 Git 版本控制；
- `cases/` 默认不进入 Git；
- Obsidian 会话报告默认本地保存并被 `.gitignore` 忽略；
- 敏感字段在日志中脱敏；
- 原始合同、发票和流水不自动复制到仓库；
- 后续如需团队协作，应增加本地数据库和权限控制，不直接通过公共 Git 同步案件。

## 7. 接口设计

内部核心接口：

```python
class FactGraphService:
    def create_case(self, payload: dict) -> Case
    def confirm_fact(self, case_id: str, fact_id: str, value: object) -> FactVersion
    def revise_fact(self, case_id: str, fact_id: str, value: object) -> ImpactSet

class IssueEngine:
    def identify(self, case: Case) -> list[TaxIssue]

class RuleEngine:
    def evaluate(self, issue: TaxIssue, facts: FactGraph, valid_on: date) -> RuleEvaluation

class VatCalculator:
    def calculate(self, context: CalculationContext) -> CalculationResult

class ScenarioEngine:
    def generate(self, case: Case, evaluations: list[RuleEvaluation]) -> list[Scenario]
    def rank(self, scenarios: list[Scenario], objective: PlanningObjective) -> list[ScenarioScore]

class CaseWorkflow:
    def advance(self, case_id: str) -> CaseState
    def replay_from(self, case_id: str, node: str) -> CaseState
```

对外 HTTP 接口第一阶段只监听 `127.0.0.1`：

- `POST /api/cases`：创建案件；
- `GET /api/cases/{id}`：读取案件；
- `PATCH /api/cases/{id}/facts/{fact_id}`：确认或修改事实；
- `POST /api/cases/{id}/analyze`：运行议题、规则和计算；
- `POST /api/cases/{id}/scenarios`：生成方案；
- `POST /api/cases/{id}/review`：记录人工审签；
- `GET /api/cases/{id}/audit`：读取审计轨迹。

## 8. 用户交互设计

V7.0 页面采用案件工作台，而不是单一长表单。

页面分区：

- 左侧：主体、交易、合同和资料；
- 中部：税务议题、计算结果和方案比较；
- 右侧：法规条款、规则命中和风险；
- 底部：案件时间线和人工审签。

交互步骤：

1. 创建案件和输入业务描述；
2. 系统生成候选事实；
3. 用户逐项确认事实；
4. 系统展示税务议题树；
5. 补充缺失事实；
6. 运行规则和计算；
7. 展示基线和多个方案；
8. 修改变量并实时重算；
9. 高风险方案提交人工审签；
10. 保存 Obsidian 报告。

第一阶段可以保留表单输入，不强制接入 LLM。自然语言访谈作为可替换入口，不能阻塞决策内核交付。

## 9. 错误处理与安全策略

### 9.1 事实错误

- 必填事实缺失：返回 `insufficient_facts`；
- 事实相互矛盾：案件状态转为 `facts_pending_confirmation`；
- 用户修改已确认事实：生成新版本，不覆盖旧版本。

### 9.2 规则错误

- 规则语法错误：启动或发布时失败；
- 多条同优先级规则输出冲突结果：返回 `conflict` 并要求人工复核；
- 找不到适用规则：不使用 LLM 猜测，返回证据不足。

### 9.3 计算错误

- 缺少计税依据或税率：输出无法计算及缺失字段；
- 金额精度错误：拒绝执行；
- 公式异常：记录完整输入、规则和版本，但日志脱敏。

### 9.4 高风险门禁

以下事项强制人工复核：

- 关联交易和主体分拆；
- 海南享惠主体、HS 编码、加工增值和零关税；
- 跨境、重组、不动产、历史补税和稽查；
- 法规冲突或只有 B/C 级证据；
- 方案依赖尚未确认的资格；
- 税额超过可配置阈值。

## 10. 测试设计

### 10.1 单元测试

- 事实节点和关系校验；
- 事实版本和影响范围；
- YAML 规则解析；
- 条件运算符；
- 地域叠加和有效期；
- 规则冲突；
- Decimal 税额计算；
- 情景生成和非法组合排除；
- 方案评分可解释性；
- 状态迁移和非法迁移拒绝。

### 10.2 黄金案例测试

至少建立以下案例：

1. 新疆小规模企业季度销售额 24 万元、普通发票；
2. 新疆小规模企业季度销售额 40 万元、普通服务；
3. 小规模纳税人放弃免税开具专票；
4. 年销售额接近和超过 500 万元；
5. 海南普通软件咨询，不触发零关税；
6. 海南进口设备但缺少 HS 编码；
7. 海南进口设备资料齐全但资格需人工确认；
8. 关联主体分拆销售额；
9. 2028 年查询 2026—2027 临时优惠；
10. 法规规则更新后历史案件影响标记。

每个黄金案例校验：

- 识别的议题；
- 命中的规则；
- 排除的规则；
- 计算结果；
- 方案数量和排序；
- 风险门禁；
- 法规引用；
- 审计轨迹。

### 10.3 属性和边界测试

- 金额等于起征点；
- 金额比起征点多 0.01 元；
- 有效期第一天和最后一天；
- 同一案件修改日期跨越政策期限；
- 含税和不含税转换一致性；
- 方案税额不应为负；
- 修改不相关事实不应触发全部重算。

### 10.4 回归测试

现有 V5/V6 的 11 项工具测试、18 项工作台测试和 17 个检索问题必须继续通过。V7 新测试与旧测试分层运行，任何规则变更必须附带对应回归案例。

## 11. 迁移策略

V6 的 `TaxFacts` 扁平模型继续作为兼容输入适配器：

```text
V6 TaxFacts
→ LegacyFactsAdapter
→ V7 FactGraph
```

V6 固定方案服务不立即删除，而是作为对照基线保留。V7 输出通过黄金案例后，再将浏览器工作台默认切换到 V7；切换前用户可在页面中选择“V6 模板模式”或“V7 决策模式”。

现有法规 Markdown、条款卡和 BM25 检索继续使用，不做破坏性迁移。新增规则 DSL 引用现有 `document_id` 和 `provision_id`。

## 12. 分阶段交付

### 阶段 A：决策内核基础

- 事实图谱；
- 案件存储；
- 税务议题树；
- 状态机；
- 审计事件。

### 阶段 B：规则与计算

- YAML 规则 DSL；
- 增值税首批规则；
- 增值税计算器；
- 规则命中解释。

### 阶段 C：情景模拟

- 合法决策变量；
- 基线和替代方案；
- 现金流时间；
- 方案评分和敏感性分析。

### 阶段 D：工作台接入

- 案件式页面；
- 事实确认；
- 方案比较；
- 人工审签；
- Obsidian 报告。

### 阶段 E：法规变化重算

- 规则与案件影响索引；
- `affected_by_law_change` 状态；
- 差异报告；
- 按需重算。

## 13. 验收标准

V7.0 第一阶段完成需要同时满足：

1. 同一案件修改金额、日期、发票需求或身份后，系统生成新事实版本并重算受影响节点；
2. 起征点、1% 政策等核心逻辑完全从业务代码移出，由规则 DSL 驱动；
3. 所有税额使用 Decimal 计算并展示公式；
4. 每个方案均展示事实、规则、法规、计算和风险来源；
5. 海南普通服务不会触发零关税；
6. 海南进口缺少 HS 编码或主体资格时不得输出优惠确定结论；
7. 关联分拆自动触发人工审签；
8. 法规有效期变化能标记受影响历史案件；
9. 黄金案例全部通过；
10. V5/V6 既有回归测试不退化；
11. 敏感案件数据默认不进入 Git；
12. 系统在没有 LLM 的情况下仍可完成确定性分析和方案比较。

## 14. 设计结论

V7.0 的核心不是增加更多聊天能力，而是建立可复用、可计算、可回放、可审计的税务决策内核。

第一版只实现增值税的有限规则和计算，但模块边界必须允许后续增加企业所得税、个人所得税、印花税、契税、土地增值税和海南进口税费，而无需重写事实图谱、案件状态和方案引擎。
